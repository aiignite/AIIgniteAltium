# 让大模型在硬件设计中实现最大程度辅助 — 架构分析报告

> 项目：AIDriveAltium · 日期：2026-09-19 · 状态：已确认的设计原则，约束 M0 起的实现
> 关联文档：已批准的《AIDriveAltium 实施方案》（见会话记录 / README）

## 0. 结论摘要

**最大辅助程度 = 感知 × 行动 × 验证 × 知识 × 编排 × 信任**

六个因子是**乘法关系**：任何一个为零，整体辅助程度为零。

- 看不见设计（感知=0）→ 只能泛泛而谈，沦为普通聊天机器人；
- 看得见不能动（行动=0）→ 只是审查报告生成器；
- 能动不能自检（验证=0）→ 写操作永远锁死在"逐步人工确认"，辅助深度上不去；
- 没有领域知识（知识=0）→ 建议不专业，用户不信任；
- 没有流程编排（编排=0）→ 每次对话都要用户重新交代上下文，退化成问答；
- 没有信任机制（信任=0）→ 用户不敢放开权限，能力再强也用不起来。

行业参照（Flux.ai、Quilter、JITX、Celus、eda-agent）共同验证的分工原则：
**LLM 负责"理解 + 决策 + 解释"，确定性引擎负责"几何 + 验证"。**
把 LLM 放进"感知 → 理解 → 决策 → 行动 → 验证 → 修正"的闭环驾驶位，是这个系统的全部架构意义。

## 1. 能力边界：大模型在硬件设计中擅长什么、不擅长什么

| 擅长（放进驾驶位） | 不擅长（交给确定性引擎） |
|---|---|
| 知识密集型判断：器件选型、方案架构、规范解读（IPC/GB）、datasheet 综合 | 精确几何计算：坐标、间距、铺铜形状 |
| 语言 ↔ 结构转换：需求 → 方案文档/网表/脚本/约束 | 数值优化：布局布线求解（Quilter 的领域） |
| 模式识别 + 解释：规则命中后的原因分析与修复建议 | 海量对象遍历：数万 pad/track 的扫描 |
| 流程编排：多阶段工作流规划、子任务分解与调度 | 确定性校验：DRC/ERC 通过与否的最终裁定 |
| 代码/脚本生成：DelphiScript、参数化片段、测试脚本 | 事实记忆：元件参数必须实时查库校验，不能靠模型记忆 |

**设计推论**：凡是"让 LLM 算坐标、背参数、跑几何"的设计都是反模式；凡是 LLM 的输出，必须有确定性验证器兜底。

## 2. 六个因子的落地设计

### 2.1 感知：让模型"看见"设计（上下文工程，第一瓶颈）

一块中等复杂度 PCB 有数千网络、数万图元，远超任何模型上下文。感知通道必须分层：

1. **归一化设计模型（Design Snapshot）＝ 硬件的"源代码层"** —— 本系统最核心的抽象。
   KiCad 的 LLM 生态强，很大程度因为其文件是 ASCII 文本，模型可直接读写；Altium 是二进制 OLE 格式且无 headless API。因此我们必须自建"文本层"：实时桥查询与离线解析统一为同一内部模型（元件/网络/PCB 几何/叠层/规则/BOM 快照）。**有了这一层，硬件设计才具备了与 agentic coding 同构的"可文本化工作对象"。**
   落点：`modules/altium/design_snapshot.py`（M1 起随 tools 同步设计）。
2. **渐进披露（Progressive Disclosure）**：项目摘要 → 板级概览（层数/尺寸/器件数/电源树）→ 网络级细节 → 元件级参数。系统提示词只注入前两级，细节数据由 agent 用查询工具按需拉取（agentic search over design data），而不是一次性塞入。
3. **视觉通道**：`take_screenshot` 回传原理图/PCB/3D 截图，走 VLM 多模态。视觉负责"整体观感与异常直觉"（布局是否拥挤、丝印是否重叠），结构化快照负责精确数据，两者互补。
4. **实时状态同步**：设计变更事件（文档切换、对象修改）推送到会话，防止 agent 基于过期快照决策。
5. **会话记忆**：审查结论、用户偏好、已确认的约束（如"该板用 JLC 焊接"）入会话上下文与数据库，跨轮次保留。

### 2.2 行动：让模型"动手"（工具分层决定 LLM 的智商上限）

工具集是给 LLM 的"指令集架构"，按三层设计：

1. **意图层（高层工具，LLM 的主战场）**：以设计意图为粒度，把几何计算封装进工具内部。
   例：`add_decoupling_network(ic_ref, spec)`（自动算去耦电容数量/容值/摆放）、`fanout_bga(ref)`、`add_testpoints(net_group, rule)`。LLM 擅长决策"该不该、要多少、什么规格"，工具负责"放哪里、怎么放"。
2. **原语层（低层正交操作）**：`place_component`、`move_objects`、`set_parameter`、`add_track` 等。供意图层组合，也供人直接点名操作（"把 C12 挪到板背面"）。
3. **逃生舱（脚本生成）**：长尾需求由 LLM 现场生成 DelphiScript，沙盒执行（超时/崩溃检测/结果回读）。这是覆盖无限需求的关键，也是 JITX"代码生成式设计"模式的低成本近似——**LLM 写脚本批量生成设计，而不是逐点模拟人点菜单**。
4. **设计查询语言（语义查询工具）**：把 Altium PCB Query 封装为语义化查询：`find_pins(filter="power pins without decoupling cap on same net")`。查询工具的质量直接决定 agent 自查能力。
5. **写操作纪律**：写工具必须返回结构化结果（改了什么/前后状态），且全部落入审计日志；不可逆操作前自动生成快照（Altium 内 `save-as` 或文件级备份）。

### 2.3 验证：让模型"自我修正"（辅助质量的决定因素）

Agentic coding 的成功公式 = LLM 写代码 + 测试反馈循环。硬件对应物：

1. **规则引擎即"测试框架"**：`eda_algorithms` 的 ERC/DRC/DFM 规则执行器就是硬件的 pytest。LLM 的任何设计变更必须通过确定性验证。
2. **写后即查（Post-Action Verification，固化进 agent loop）**：orchestrator 在每次写工具成功后自动触发关联规则子集重查，结果回喂模型；不通过则进入"分析 → 修正 → 重查"循环（设最大轮数，超限转人工）。这一步是 L2 → L3 的门槛。
3. **视觉复检**：写操作前后截图对比，供模型与用户确认视觉效果。
4. **仿真接口（预留）**：电源完整性/热/信号完整性等重型验证后续以工具形式接入，接口与规则引擎统一（输入设计快照，输出结构化 findings）。

### 2.4 知识：领域增强（决定建议的专业度上限）

1. **RAG 知识库**（`modules/rag`，pgvector）：企业设计规范、IPC/GB 标准、内部 checklists、datasheet 结构化摘要。审查类技能的回答必须带引用（规范条款号/datasheet 页码），可核查才可信。
2. **元件实时数据**（`modules/components`）：Nexar/Octopart + Digi-Key + jlcparts 三源，带本地缓存；替代料匹配、生命周期(EOL/NRND)、供应链风险。**模型永远不凭记忆回答参数，查库后引用**。
3. **案例库（数据飞轮的起点）**：每次审查报告、每条缺陷命中、每个人工修正都结构化入库。案例库既提升后续审查（few-shot 检索），又是评测集的原料。
4. **模型分层降本**：大模型做推理决策；小模型/嵌入模型做 datasheet 参数抽取、规则分类；敏感数据可切本地 Ollama（沿 AIIgnitePLM 多 provider 架构）。

### 2.5 编排：全流程覆盖（阶段化技能 + 多 agent）

沿 AIIgnitePLM 的 V 模型技能编排，映射硬件流程：

| 阶段 | LLM 职责 | 人 | 关键技能 |
|---|---|---|---|
| 需求分析 | 需求结构化、关键器件预选、方案对比 | 确认需求基线 | `requirement-analysis` |
| 方案设计 | 系统框图、电源树/接口规划、BOM 骨架 | 方案拍板 | `solution-design` |
| 原理图 | 网表级审查、参考设计比对、ERC 修复建议 | 绘图决策 | `schematic-review` |
| PCB | 规则审查、布局建议、意图级操作执行 | 布局创意决策 | `pcb-review` `placement-assist` |
| 可制造性 | 厂家能力比对、DFM 报告 | 工艺确认 | `dfm-review` |
| BOM/投产 | 选型替代、风险清单、成本优化 | 采购决策 | `bom-selection` |

模式：**计划-执行分离**（L3 起用户审批计划 → agent 多步执行 → 逐项验证 → 汇报）；阶段产物（快照+报告）作为下一阶段上下文。

### 2.6 信任：辅助级别分级与"可调门"（决定用户敢放开多少权限）

定义辅助级别 L0–L4，权限随验证闭环的可靠性数据逐步放开：

| 级别 | 形态 | 对应里程碑 |
|---|---|---|
| L0 问答 | 查询设计信息与知识 | M0–M1 |
| L1 审查 | 读设计 + 知识，输出结构化问题清单与建议 | M2–M3 |
| L2 单步执行 | 确认后执行单个写操作 | M1/M5 |
| L3 任务级自主 | 审批计划 → 多步执行 → 自验证 → 汇报 | M5 |
| L4 阶段级自主 | 整阶段自动化（如"完成 12 颗 IC 去耦布局并过 DRC"） | 远期，依赖评测数据 |

配套机制：
- **确认门槛引擎**：操作按可逆性/影响域分类（只读=0 门槛；可逆写=轻确认；不可逆/批量=重确认+快照），门槛随操作历史成功率可配置下调；
- **透明度**：前端 ToolCallDisplay 展示每步工具调用与参数、审查结论带规则条款引用——可解释才有信任；
- **审计**：全部写操作入库（谁/何时/改了什么/依据哪个建议/是否被撤销）。

## 3. 对已批准方案的增量修订（纳入实现约束）

1. **验证闭环总线**：ai_engine orchestrator 的 agent loop 固化 `post-action verification` 环节（M5 前以"审查工具自动调用约定"过渡）。
2. **设计查询工具**：gateway tools 从 M1 起即按语义查询风格设计（`find_*` 系列 + filter 表达式），而非只做全量导出。
3. **案例库**：`modules/review` 增加 findings/案例结构化表，作为 RAG 数据源之一（M3）。
4. **评测集**：`docs/evals/` + 金标准缺陷板样例工程；审查查全率/误报率作为北极星指标，CI 跑审查回归（M3 起建）。
5. **确认门槛引擎**：写操作分类表 + 审计日志为 M5 前置依赖，M1 的工具定义即包含分类元数据。

## 4. 反模式清单（明确不做）

- ❌ 让 LLM 直接输出坐标/几何参数（应由意图工具换算）；
- ❌ 全板数据一次性入 context（必须渐进披露 + 查询工具）；
- ❌ 无验证器的自由写操作（每写必查）；
- ❌ 以"端到端全自动布局布线"为第一目标（那是 Quilter 的领域，作为远期外接能力）;
- ❌ 用微调替代工具/上下文工程（先 prompt+RAG+工具，案例库形成数据飞轮后再评估小模型微调）；
- ❌ 无评测迭代（没有金标准集，"最大辅助"无法度量）。

## 5. 度量体系（北极星指标）

| 维度 | 指标 | 目标锚点 |
|---|---|---|
| 审查质量 | 金标准集查全率 / 误报率 | 查全 ≥ 人工自检均值，误报可控 |
| 执行能力 | 任务完成率、每任务人工干预次数、写后重查一次通过率 | 干预次数随版本下降 |
| 效率 | 各阶段耗时 vs 无辅助基线 | 审查类阶段 ≥ 50% 提速 |
| 信任增长 | 自动执行(L3+)操作占比随时间曲线 | 持续上升且事故为零 |
